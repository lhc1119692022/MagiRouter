# 分支与发布流程

本文件描述 MagiRouter 这个 Fork 的协作方式：如何接收上游更新、如何改造、如何发布、
以及上线后如何确认「线上跑的就是这份代码」。

## 一、仓库关系

| 远程 | 地址 | 权限 | 用途 |
| --- | --- | --- | --- |
| `upstream` | `https://github.com/QuantumNous/new-api.git` | 只读 | 官方仓库，唯一的上游真相 |
| `origin` | `https://github.com/lhc1119692022/MagiRouter.git` | 可写 | 自己的 Fork，保存全部定制 |

`upstream` 的推送地址已被设为 `no-push`，避免手滑把定制推到官方仓库。
需要恢复时执行 `git remote set-url --push upstream <官方地址>`。

## 二、分支

| 分支 | 作用 | 规则 |
| --- | --- | --- |
| `main` | 上游镜像 | 只允许快进（fast-forward），不放任何自有改动 |
| `magirouter` | 实际部署分支 | 所有定制都在这里，发布也只从这里出 |

`main` 保持干净的意义：任何时候都能用 `git diff main magirouter` 一眼看出我们改了什么，
也能在合并冲突时把 `main` 当作「上游原本长什么样」的参照。

## 三、日常循环（接收上游更新）

```bash
# 1. 拉取上游
git fetch upstream --prune --tags

# 2. 看一眼差多少（也可以在网站后台 /system-info「上游同步」里看）
git log --oneline HEAD..upstream/main

# 3. 合并
git switch magirouter
git merge upstream/main
```

冲突通常只出现在 `web/src/i18n/locales/*.json`：两边都在文件末尾新增词条，
按「取并集」处理即可，原有键一个都不能删。

只有在上游 ALSO 修改了我们改过的同一个组件时，才需要人工判断。当前定制的边界
（见《定制清单》）集中在 `web/src/features/magirouter-home`、`features/docs`、
`features/upstream-sync` 等新增目录，上游几乎不会碰，冲突面很小。

## 四、发布

发布脚本会做三件事：给版本号打上「本次提交 + 上游基线」印记、构建前端、
（可选）构建并推送镜像。

```powershell
.\scripts\release.ps1                                        # 只构建前端
.\scripts\release.ps1 -Image ghcr.io/lhc1119692022/magirouter -PushImage
```

版本号格式：

```
v1.0.0-rc.51+sha.<本次提交>.up.<上游基线提交>
```

- `v1.0.0-rc.51` 是本次构建所基于的上游发布版本（默认取上游最新 tag）。
- `sha.<...>` 是构建时 HEAD 的提交号。
- `up.<...>` 是最后一次合并进来的上游提交（`git merge-base HEAD upstream/main`）。

脚本只在构建期间把版本号写进 `VERSION`（Go 编译时通过 `-X common.Version` 嵌入），
构建结束立刻还原，工作区保持干净。因此**不要手工修改 `VERSION`**，
它会随每次发布自动生成。

构建产物里同时会生成 `web/dist/version.json`，内容与版本号一致，便于静态部署核对。

## 五、上线后核对

1. 打开 `https://<你的域名>/api/status`，确认 `version` 与发布时打印的版本号一致。
2. 用管理员登录，进入「系统信息 → 上游同步」：
   - 「当前线上构建」应显示刚发布的提交号；
   - 「上游基线」应显示合并时的上游提交；
   - 「落后 N 个提交」为 0 或符合预期。
3. 若面板显示「本次构建没有记录上游基线」，说明这次部署不是用发布脚本构建的，
   线上代码与仓库的对应关系无法自证，应重新用脚本发布。

## 六、回滚

镜像是按版本号打 tag 的，回滚就是把旧 tag 重新拉起：

```bash
docker pull <镜像>:<旧版本号>
docker compose up -d
```

回滚后 `/api/status` 的 version 会回到旧值，面板也会据此显示与上游的真实差距。

## 七、禁止事项

- 不要在服务器上直接改文件或替换 `dist`：线上会失去可追溯性。
- 不要向 `main` 提交自有改动，也不要 force push。
- 不要用未打版本印记的构建上线，否则面板无法判断线上落后多少。
- 合并上游后必须重新构建；仅合并代码不重新发布，线上仍是旧版本。
